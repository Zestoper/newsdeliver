## 1. FastAPI 관련

### Q. FastAPI를 선택한 이유는? Flask나 Django와 비교해서 설명하세요.
**A.**
- FastAPI는 Python 타입 힌트 기반으로 자동 문서화(Swagger/ReDoc)가 되고, 비동기(async/await)를 기본 지원합니다.
- Flask는 경량이지만 async 지원이 약하고 자동 문서화가 없습니다.
- Django는 풀스택 프레임워크로 ORM, 관리자 페이지 등이 내장되어 있지만 무겁고 설정이 복잡합니다.
- 이 프로젝트에서는 뉴스 수집(RSS 크롤링), 뉴스레터 발송, 실시간 채팅(WebSocket) 등 I/O 집약 작업이 많아 FastAPI의 비동기 처리가 적합했습니다.

### Q. FastAPI의 lifespan이란 무엇인가요?
**A.**
- 서버 시작/종료 시 실행할 코드를 관리하는 context manager입니다.
- `@asynccontextmanager`로 장식한 함수를 `FastAPI(lifespan=...)` 에 전달합니다.
- `yield` 전 코드는 서버 시작 시 실행(APScheduler 시작, DB 연결 확인 등), `yield` 후 코드는 종료 시 실행(scheduler.shutdown())합니다.
- 이 프로젝트에서는 서버 시작 시 뉴스 초기 수집 스레드를 띄우고 스케줄러를 시작합니다.

## 2. 인증 관련

### Q. JWT 대신 쿠키 기반 세션 인증을 쓴 이유는?
**A.**
- 이 프로젝트는 SSR(Jinja2 템플릿)로 구성되어 있어 서버에서 HTML을 렌더링하는 구조입니다.
- 쿠키는 브라우저가 자동으로 서버에 전송하므로 별도의 클라이언트 코드 없이 인증이 됩니다.
- `httponly=True`로 JavaScript가 쿠키에 접근하지 못하게 해 XSS 공격을 방어했습니다.
- `samesite="lax"`로 CSRF 공격을 방어했습니다.
- JWT는 stateless 토큰 방식으로 SPA/모바일 앱에 적합하지만, 이 프로젝트 구조에서는 쿠키 방식이 더 단순합니다.

### Q. httponly 쿠키란 무엇이고 왜 쓰나요?
**A.**
- `httponly=True`로 설정된 쿠키는 JavaScript의 `document.cookie`로 접근할 수 없습니다.
- XSS(Cross-Site Scripting) 공격자가 악성 스크립트를 심어도 인증 쿠키를 탈취할 수 없습니다.
- 이 프로젝트에서 `newsletter_user` 쿠키에 user_id를 저장할 때 이 옵션을 사용했습니다.

### Q. OAuth 2.0 Authorization Code Flow를 설명하세요.
**A.**
1. 유저가 "카카오로 로그인" 버튼 클릭 → `/oauth/kakao` 요청
2. 서버가 카카오 인증 URL로 리다이렉트 (client_id, redirect_uri, response_type=code 포함)
3. 유저가 카카오에서 로그인/동의 후 → 카카오가 `redirect_uri`로 `code` 파라미터와 함께 리다이렉트
4. 서버가 code를 카카오 토큰 엔드포인트에 POST하여 access_token 발급
5. access_token으로 카카오 사용자 정보 API 호출
6. DB에 사용자 upsert 후 자체 쿠키 발급하여 로그인 완료

## 3. 데이터베이스 관련

### Q. SQLAlchemy ORM 대신 Core(raw SQL)를 사용한 이유는?
**A.**
- ORM은 클래스 모델 정의가 필요하고 복잡한 JOIN 쿼리에서 성능이 떨어질 수 있습니다.
- 이 프로젝트는 뉴스 집계, 카테고리별 필터, 댓글+좋아요 COUNT JOIN 등 복잡한 쿼리가 많아 raw SQL이 더 직관적입니다.
- `text()` 함수로 SQL injection을 방어하면서 named parameter(`:param` 형식)를 사용했습니다.
- `ON CONFLICT DO NOTHING`으로 중복 기사 삽입 시 오류 없이 처리합니다.

### Q. 데이터베이스 마이그레이션을 어떻게 처리했나요?
**A.**
- Alembic 같은 전용 도구 대신 서버 시작 시 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 방식으로 직접 마이그레이션을 실행합니다.
- `IF NOT EXISTS`로 멱등성(idempotent)을 보장하여 서버를 재시작해도 중복 실행되지 않습니다.
- 각 마이그레이션을 try/except로 감싸 실패 시 `conn.rollback()` 후 다음 마이그레이션을 계속 진행합니다.
- 단점: 롤백 기능이 없고, 복잡한 마이그레이션(컬럼 타입 변경 등)엔 적합하지 않습니다.

### Q. PostgreSQL에서 `ON CONFLICT DO NOTHING`이란?
**A.**
- INSERT 시 UNIQUE 제약조건이 걸린 컬럼에 중복 값이 들어오면 오류 대신 아무것도 하지 않고 넘어갑니다.
- 이 프로젝트에서 뉴스 제목(title)에 UNIQUE 인덱스를 걸고, 같은 기사가 중복 수집될 때 이 구문으로 조용히 무시합니다.

## 4. 비동기/스레딩 관련

### Q. APScheduler로 어떻게 정기 작업을 구현했나요?
**A.**
- `BackgroundScheduler`는 백그라운드 스레드에서 실행되는 스케줄러입니다.
- `CronTrigger`로 특정 시간을 지정합니다:
  - 뉴스레터 발송: 매일 07:30, 18:30 KST
  - 뉴스 자동수집: 2시간마다 (`hour="*/2"`)
- 스케줄러는 FastAPI 앱과 별도 스레드에서 실행되므로 async 함수가 아닌 일반 함수를 등록합니다.

### Q. threading.Lock()을 Groq API 호출에 사용한 이유는?
**A.**
- Groq API는 분당 10회 요청 제한이 있습니다 (`_MIN_INTERVAL = 6.0`초).
- 뉴스레터 발송 시 여러 기사의 AI 요약을 동시에 생성하면 rate limit(429 오류)이 발생합니다.
- `threading.Lock()`으로 동시에 하나의 스레드만 Groq API를 호출하도록 직렬화합니다.
- Lock 블록 안에서 마지막 호출 시간을 체크해 6초 미만이면 sleep합니다.

### Q. ThreadPoolExecutor를 해외뉴스 수집에 쓴 이유는?
**A.**
- RSS 피드가 50개 이상이며 각각 HTTP 요청이 필요합니다.
- 순차 수집하면 수십 초가 걸립니다.
- `ThreadPoolExecutor(max_workers=12)`로 최대 12개 피드를 동시에 수집합니다.
- `as_completed(timeout=45)`로 45초 이내에 완료된 것만 처리합니다.

## 5. 외부 API / 서비스 관련

### Q. 네이버 뉴스 API와 RSS 피드를 각각 어떻게 사용했나요?
**A.**
- **국내뉴스 (네이버)**: 네이버 검색 API로 카테고리별 키워드 검색 → 기사 URL 획득 → `extract_full_content()`로 본문 직접 크롤링
- **해외뉴스 (RSS)**: feedparser로 NYT, BBC, WSJ, Guardian, LA Times 등 50개 이상의 RSS 피드를 파싱 → 기사 제목/본문/이미지 추출

### Q. 해외뉴스 본문이 없는 경우 어떻게 처리했나요?
**A.**
- RSS entry에는 `content` 필드와 `summary` 필드가 있습니다.
- `content`가 `summary`보다 길면 `content`를 사용하고, 그렇지 않으면 `summary`를 사용합니다.
- 최악의 경우 제목으로 대체합니다.

### Q. 뉴스 본문 크롤링(extract_full_content)의 4단계 폴백이란?
**A.**
1. **id 속성 탐색**: `dic_area`, `articleBodyContents` 등 알려진 id 선택자로 본문 영역 탐색
2. **class 속성 탐색**: `article-body`, `entry-content` 등 class 선택자로 탐색
3. **시맨틱 태그 폴백**: `<article>`, `<main>` 태그에서 본문 추출
4. **`<p>` 태그 수집**: 30자 이상의 `<p>` 태그를 모두 수집해 이어붙임

BeautifulSoup 없이 `re`와 문자열 `find()`만 사용해 의존성을 최소화했습니다.

### Q. SMTP로 이메일을 보낼 때 `starttls()`를 쓰는 이유는?
**A.**
- SMTP는 기본적으로 평문(plaintext) 통신입니다.
- `starttls()`로 TLS 암호화로 업그레이드하여 인증정보(Gmail 비밀번호)와 이메일 내용을 암호화합니다.
- Gmail의 경우 포트 587에서 STARTTLS를 사용합니다 (포트 465는 SMTPS로 처음부터 TLS).

## 6. 카테고리 분류 관련

### Q. 해외뉴스를 어떻게 카테고리로 분류했나요?
**A.**
- `_classify()` 함수에서 카테고리별 필수 키워드 목록(`REQUIRED` 딕셔너리)을 기반으로 점수를 계산합니다.
- 제목 매치는 2점, 설명 매치는 1점으로 가중치를 줍니다.
- 가장 높은 점수의 카테고리로 분류하되, RSS 소스의 힌트 카테고리도 고려합니다.
- 미국 정치 인물(trump, biden 등) 키워드가 포함된 기사는 `POLITICS_BLOCK_TERMS`로 별도 처리하여 경제/국제/정치 카테고리 중 적절한 곳으로 라우팅합니다.

## 7. 보안 관련

### Q. SQL injection을 어떻게 방어했나요?
**A.**
- SQLAlchemy `text()`와 named parameter(`:param` 방식)를 사용했습니다.
- 예: `text("SELECT * FROM news WHERE id = :id")` + `{"id": news_id}`
- 사용자 입력값이 SQL 쿼리 문자열에 직접 삽입되지 않아 injection이 불가능합니다.
- 단, 일부 동적 쿼리에서 f-string으로 WHERE절을 구성하는 부분은 외부 입력이 아닌 내부 로직에서만 조건을 생성하도록 설계했습니다.

### Q. CORS를 `allow_origins=["*"]`로 설정한 것의 위험성은?
**A.**
- 모든 출처(origin)에서 API 요청을 허용하므로 다른 웹사이트가 사용자 브라우저를 통해 이 서버에 요청을 보낼 수 있습니다.
- 쿠키 인증을 사용하는 경우 `allow_credentials=True`와 함께 `*`를 쓸 수 없지만 (브라우저가 차단), 이 프로젝트의 SSR 구조에서는 실질적 위험이 낮습니다.
- 프로덕션에서는 `allow_origins=["https://yourdomain.com"]`으로 명시적으로 제한해야 합니다.

## 8. WebSocket 관련

### Q. WebSocket과 HTTP의 차이점은?
**A.**
- HTTP는 요청-응답 방식으로 클라이언트가 요청해야만 서버가 응답합니다.
- WebSocket은 한 번 연결(handshake)하면 양방향 실시간 통신이 가능합니다.
- 이 프로젝트의 채팅 기능에서 관리자가 메시지를 보내면 서버가 클라이언트 폴링 없이 바로 전달합니다.
- `_ConnectionManager.broadcast()`로 같은 채팅방의 모든 연결된 클라이언트에게 메시지를 전송합니다.
